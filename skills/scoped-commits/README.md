# scoped-commits

커밋 하나가 **혼자 읽었을 때 하나의 이야기**가 되게 나누고, 무엇을 했는지가 아니라 **어느 영역을 건드렸는지**를 제목 앞에 세운다. 제목은 `<scope>: <설명>`, 본문은 모든 커밋에 쓴다.

이 문서는 **구조와 왜**를 적는다. 규칙 원문과 값 — 제목 폭, type 목록, 검사 항목, 설치 명령 — 은 아래 세 곳에 살고 여기서는 링크만 한다. 같은 값을 두 곳에 적으면 갈리고, 갈린 것을 아무도 알아채지 못한다. 이 저장소가 실제로 밟은 구멍이다(제목 폭이 세 자리에 서로 다르게 남아 규칙을 위반한 제목이 훅을 통과했다).

## 구조 — 세 층

| 층 | 어디 | 하는 일 |
|---|---|---|
| 의미 | [`SKILL.md`](SKILL.md) | 워킹트리를 **무엇을 한 커밋으로 묶을지**로 나눈다 |
| 형식 | [`messages.md`](messages.md) | scope·제목·본문을 **어떻게 쓸지**. 규칙 원문이다 |
| 강제 | [`githooks/`](githooks/README.md) | 커밋 직전에 **정적으로 판정 가능한 것만** 거부한다 |

능력으로 갈린 층이다. 훅은 diff 의 의미를 모르니 분할을 판정할 수 없고, 스킬은 다른 도구가 만드는 커밋을 막을 수 없다. 각 층은 자기가 할 수 있는 것만 맡고, 못 하는 것을 떠안지 않는다.

## 설계 판단

**층을 가로지르는 판단만 여기 있다.** 한 층 안에서 닫히는 것 — 훅을 어떻게 배선하는지, 절차가 언제 승인을 받는지 — 은 그 층의 문서가 갖는다.

### type 접두어를 버리고 scope 를 앞에 둔다

`feat:`·`fix:` 같은 type 은 대체로 한 값에 쏠려서 제목의 앞자리만 먹는다. 로그를 훑는 사람이 알고 싶은 것은 변경의 종류가 아니라 어느 영역을 건드렸는가다. 그 자리를 영역 이름에 준다.

### scope 는 파일명이 아니다

파일명·디렉토리명을 그대로 쓰면 그 파일의 **모든 커밋에 같은 이름이 붙어** 아무것도 구별하지 못한다. scope 는 이 커밋이 바꾼 함수·상수·규칙의 공통 목적을 가리키는 이름이다. 한 파일 안에 여러 영역이 살기 때문에, 같은 파일을 건드렸다는 사실은 같은 영역이라는 근거가 되지 못한다.

훅도 이걸 검사한다 — scope 가 스테이징된 경로의 이름이면 거부한다. 정적으로 판정할 수 있는 몇 안 되는 의미 규칙이라서다.

### 분할을 정하는 동안 메시지 규칙을 읽지 않는다

이 스킬에서 가장 독특한 설계다. `SKILL.md` 는 분할이 확정되기 전에 `messages.md` 를 열지 말라고 명시한다.

컨텍스트에 무엇이 있느냐가 판단을 흔들기 때문이다. 같은 변경에 의미 규칙만 줬을 때 커밋 수가 4·4·4로 일치했고, 메시지 규칙을 함께 줬을 때 6·8·4로 흩어졌다(실측). 메시지 규칙은 "이렇게 쓸 수 있는 단위"를 떠올리게 해서 분할을 그쪽으로 끌어당긴다.

그래서 규칙을 한 파일에 몰아넣지 않고 **읽는 시점으로 갈랐다.** 파일이 둘인 것은 분량 때문이 아니라 순서 때문이다.

### 강제는 Claude Code 가 아니라 git 에 건다

스킬만으로는 Claude Code 에서 만드는 커밋에만 걸린다. 다른 에이전트가 커밋하면 아예 돌지 않는다. 그래서 강제를 git 훅에 두어 Claude Code·Cursor·Codex·Aider·사람·CI 어디서 커밋하든 걸리게 했다.

여러 에이전트로 실측했고, 어느 쪽도 이 규약을 알아서 지키지 않았다. 숫자는 [`githooks/README.md`](githooks/README.md) 의 "왜 git 훅인가" 에 있다 — 훅을 다른 저장소로 가져갈지 판단하는 데 필요한 근거라 그쪽이 원본이다.

### 훅은 의미를 묻지 않는다

훅이 하는 판정은 전부 정적이다. **분할을 강제하지 않는다** — 형식만 맞으면 한 덩어리 커밋도 통과한다. **본문은 존재만 본다** — 최소 길이조차 두지 않았다. 길이를 재는 순간 "충분한가"라는 의미 판정이 들어오고, 그건 훅이 옳게 할 수 없는 일이다.

의미 판정을 훅에 욱여넣지 않은 대가로 분할은 스킬과 사람이 지킨다. 훅이 절반만 막는 것이 아니라, 훅이 확실히 맞출 수 있는 절반만 맡는다.

### 본문을 필수로 둔다

무엇을 했는지는 diff 가 말한다. 본문이 말해야 하는 것은 diff 에 없는 세 가지다 — 왜 했는가, 고려했다가 하지 않은 것과 그 이유, 확인하지 못한 것. 특히 두 번째가 없으면 다음 사람이 그것을 **빠뜨린 것으로 읽고 채워 넣는다.**

## 알고 남긴 구멍

강제에는 세 군데 구멍이 있다. `--no-verify` 는 훅을 통째로 건너뛰고, 메시지만 고치는 `--amend` 는 파일명 scope 검사를 지나가고, 본문이 주석 줄뿐이면 남는 본문인데도 거부된다.

셋 다 원리적으로 막을 수 없거나, 막는 비용이 값보다 컸다 — 예컨대 `--no-verify` 를 잡으려면 커밋 명령을 미리 보는 층이 필요한데, 프로토타입까지 만들고도 에이전트 10런에서 발동 0회로 값을 보인 자리가 없어 접었다. 각각의 사정은 [`githooks/README.md`](githooks/README.md) 의 "무엇을 검사하지 않는가" 에 적혀 있다.

**고치지 않은 것이 아니라 알고 남긴 것이다.** 어디까지 막히는지 알고 쓰는 것과 다 막힌다고 믿고 쓰는 것은 다르다.

## 어디를 볼 것

- [`SKILL.md`](SKILL.md) — 워킹트리를 커밋으로 만드는 절차. Claude Code 에서 `/scoped-commits` 로 부르거나 그냥 커밋을 요청하면 이걸 따른다
- [`messages.md`](messages.md) — scope·제목·본문 규칙 원문. 사람이 손으로 커밋할 때도 여기가 기준이다
- [`githooks/README.md`](githooks/README.md) — 훅 설치, 검사·미검사 항목, 이식성과 비용
