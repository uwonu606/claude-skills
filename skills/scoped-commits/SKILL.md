더러운 워킹트리를 받아 여러 개의 커밋으로 만든다. 분할을 먼저 확정하고, 확정된 뒤에야 메시지를 쓴다.

- **이미 만들어진 커밋을 고치는 요청이면** [`references/rewriting.md`](references/rewriting.md) 를 먼저 읽는다.
- **로그 전체가 규약을 지키는지 훑는 요청이면** [`references/log-audit.md`](references/log-audit.md) 를 읽는다.

**[`references/messages.md`](references/messages.md) 는 4단계에 가서 읽는다.** 분할을 판정하는 동안 메시지 규칙이 컨텍스트에 있으면 분할이 흔들린다 — 같은 변경에 의미 규칙만 주면 커밋 수가 4·4·4 로 일치했고, 메시지 규칙을 함께 주면 6·8·4 로 흩어졌다. 3단계를 끝내기 전에 열지 마라.

## 1. 무엇이 바뀌었는지 본다

`git status` 와 `git diff HEAD` 로 워킹트리 전체를 읽는다. 커밋되지 않은 변경 전부가 대상이다.

**완료 기준**: 바뀐 파일이 모두 목록에 있고, 각 파일에서 무엇이 바뀌었는지 diff 수준으로 읽었다.

## 2. 의미 단위로 나눈다

커밋 하나는 **혼자 정당화되는** 변경이다 — 그 커밋만 보고도 왜 했는지 판단할 수 있고, 왜인지를 대려고 다른 커밋을 끌어올 필요가 없다. 혼자 정당화되는 변경마다 하나씩 나눈다.

덜 쪼갠 것을 알아내는 신호가 둘이다.

- **제목에 "그리고"나 "~하고"가 필요하다.** 한 줄로 요약되면 하나고, 안 되면 둘이다.
- **설명이 자꾸 길어진다.** 왜 했는지를 적는 데 두 문단이 필요하면 더 잘게 나눌 것이 남아 있다.

**커밋은 기록이고 검증은 별개다.** 나누는 근거는 diff 가 말하는 의미 하나다 — 각 커밋이 그 시점에 빌드되는지, 테스트가 통과하는지, 혼자 되돌려지는지는 원래 작업을 한 쪽의 몫이다. 분할은 최종 트리를 바꾸지 않으므로 나누기 전과 후의 HEAD 가 같다. 실행 가능성을 diff 만 보고 판정하려는 시도는 3회 중 1회만 맞았고, 틀린 판정은 조용히 어긋난 분할을 만든다.

**제목이 아니라 diff에서 의미를 센다.** 커밋 제목이 말하지 않는 변경이 diff에 들어 있을 수 있다.

**완료 기준**: 모든 변경이 정확히 하나의 커밋에 배정됐고, 각 커밋이 혼자 정당화된다.

## 3. 분할안을 낸다

각 커밋을 **한 줄 요지 + 파일 목록**으로만 제시한다 — 제목과 본문은 4단계다.

다음 단계로 갈지는 누가 이 커밋을 시작했는가로 정한다.

- **사용자가 커밋을 지시했으면** — 이번 요청이든, 세션 중의 "알아서 커밋해" 같은 지시든 — 멈추지 말고 4단계로 간다. 분할이 틀렸으면 `git reset --soft HEAD~N` 한 줄로 풀린다 — 파일은 그대로 남고 커밋만 풀리므로, 되돌리는 비용이 매번 승인을 받는 비용보다 작다.
- **에이전트가 스스로 커밋을 시작했으면** 분할안을 보이고 승인을 받는다. 승인 전에는 4단계로 가지 않는다.

**완료 기준**: 커밋 개수와 각 커밋이 담을 것이 정해졌고 사용자에게 보였다. 스스로 시작한 커밋이면 승인까지 받았다.

## 4. 메시지를 쓰고 커밋한다

이제 [`references/messages.md`](references/messages.md) 를 읽고, 거기 적힌 대로 각 커밋의 scope·제목·본문을 쓴다.

커밋마다 해당 변경만 `git add` 로 스테이징한 뒤 커밋한다. 본문이 길면 `git commit -F -` 에 heredoc 으로 넘기는 것이 따옴표 처리가 없어 안전하다.

**완료 기준**: 워킹트리에 커밋되지 않은 변경이 남지 않았고, 만든 커밋 수가 3단계에서 정한 수와 같다.
