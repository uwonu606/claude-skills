더러운 워킹트리를 받아 여러 개의 커밋으로 만든다. 분할을 먼저 확정하고, 확정된 뒤에야 메시지를 쓴다.

**[`messages.md`](messages.md)는 4단계에 가서 읽는다.** 분할을 판정하는 동안 메시지 규칙이 컨텍스트에 있으면 분할이 흔들린다 — 같은 변경에 의미 규칙만 주면 커밋 수가 4·4·4로 일치했고, 메시지 규칙을 함께 주면 6·8·4로 흩어졌다. 3단계를 끝내기 전에 열지 마라.

규약을 강제하는 것은 저장소의 `.githooks/commit-msg` 다. 설치는 [`githooks/README.md`](githooks/README.md)를 보라.

## 1. 무엇이 바뀌었는지 본다

`git status`와 `git diff HEAD`로 워킹트리 전체를 읽는다. 커밋되지 않은 변경 전부가 대상이다.

**완료 기준**: 바뀐 파일이 모두 목록에 있고, 각 파일에서 무엇이 바뀌었는지 diff 수준으로 읽었다.

## 2. 의미 단위로 나눈다

커밋 하나는 **혼자 읽었을 때 하나의 이야기**다. 제목에 "그리고"나 "~하고"가 필요 없으면 하나다. 독립적으로 설명되는 변경마다 하나씩 나눈다.

**각 커밋이 그 시점에 빌드되는지, 테스트가 통과하는지, 혼자 되돌릴 수 있는지는 판정하지 않는다.** 커밋은 기록이고 검증은 별개다. 분할은 최종 트리를 바꾸지 않으므로 나누기 전과 후의 HEAD가 같고, 검증은 원래 작업을 한 쪽의 몫이다. 실행 가능성을 diff만 보고 판정하려는 시도는 3회 중 1회만 맞았다 — 틀린 판정은 조용히 어긋난 분할을 만든다.

**제목이 아니라 diff에서 의미를 센다.** 커밋 제목이 말하지 않는 변경이 diff에 들어 있을 수 있다.

**완료 기준**: 모든 변경이 정확히 하나의 커밋에 배정됐고, 어느 커밋도 두 가지 이야기를 담지 않는다.

## 3. 분할안을 낸다

각 커밋을 **한 줄 요지 + 파일 목록**으로 제시한다. 아직 메시지를 쓰지 마라.

다음 단계로 갈지는 누가 이 커밋을 시작했는가로 정한다.

- **사용자가 커밋을 지시했으면** — 이번 요청이든, 세션 중의 "알아서 커밋해" 같은 지시든 — 멈추지 말고 4단계로 간다. 분할이 틀렸으면 `git reset --soft HEAD~N` 한 줄로 풀린다 — 파일은 그대로 남고 커밋만 풀리므로, 되돌리는 비용이 매번 승인을 받는 비용보다 작다.
- **에이전트가 스스로 커밋을 시작했으면** 분할안을 보이고 승인을 받는다. 승인 전에는 4단계로 가지 않는다.

**완료 기준**: 커밋 개수와 각 커밋이 담을 것이 정해졌고 사용자에게 보였다. 스스로 시작한 커밋이면 승인까지 받았다.

## 4. 메시지를 쓰고 커밋한다

이제 [`messages.md`](messages.md)를 읽는다. 거기 적힌 대로 각 커밋의 scope·제목·본문을 쓴다.

해당 변경만 `git add`로 스테이징한 뒤 커밋한다. 본문이 길면 `git commit -F -`에 heredoc으로 넘기는 것이 따옴표 처리가 없어 안전하다.

**완료 기준**: 워킹트리에 커밋되지 않은 변경이 남지 않았고, 만든 커밋 수가 3단계에서 정한 수와 같다.
