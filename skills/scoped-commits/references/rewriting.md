# 이미 쓴 커밋을 다시 쓴다

`SKILL.md` 의 절차는 커밋되지 않은 변경을 다룬다. 이미 만들어진 커밋을 이 규약으로 고칠 때 이 문서를 읽는다.

## 먼저 두 가지를 가른다

**무엇을 고치는가.**

- **메시지만** — 분할은 그대로 두고 제목·본문을 다시 쓴다. 이미 conventional commits 로 쓰인 이력을 옮겨 오는 경우가 여기다.
- **분할부터** — 한 커밋에 여러 이야기가 들어 있어 나눠야 한다. 에이전트가 한 덩어리로 만든 커밋이 여기다.

애매하면 묻는다. 되돌릴 수 없는 것을 잃는 쪽이 분할이므로 기본값은 메시지만이다.

**무엇을 되돌릴 수 없는가.**

```bash
git log --oneline @{upstream}..HEAD   # 아직 푸시되지 않은 범위 (upstream 이 없으면 전부가 로컬이다)
git log --merges <범위>               # 범위에 머지가 섞였는지
```

- **푸시된 커밋을 고치면 force-push 가 필요하다.** 그것을 이미 받아 간 클론은 스스로 고쳐지지 않는다 — `git pull` 이 `refusing to merge unrelated histories` 로 멈추고, `--allow-unrelated-histories` 로 밀어붙이면 옛 커밋과 새 커밋이 나란히 남아 이력이 두 배가 된다. 사용자에게 확인을 받고 진행한다.
- **범위에 머지가 있으면 이력의 모양이 바뀐다.** `rebase -i` 는 머지를 버리고 곁가지를 본류에 직렬로 펴고, `reset --soft` 는 곁가지 작업까지 인덱스로 끌어와 본류 변경과 섞는다. 무엇이 바뀌는지 말하고 확인을 받는다.

## 메시지만 고친다

작성일이 보존된다.

```bash
git rebase -i <대상의 부모>    # 대상 줄을 pick → reword
```

에디터가 열리면 [`messages.md`](messages.md) 대로 제목과 본문을 쓴다. 여러 개를 고치려면 여러 줄을 `reword` 로 표시한다.

## 분할부터 다시 한다

```bash
git rebase -i <대상의 부모>    # 대상 줄을 pick → edit
git reset --soft HEAD~1       # 대상 커밋만 워킹트리로 되돌린다
```

여기서 `SKILL.md` 1단계로 돌아가 절차를 그대로 밟는다. 커밋을 다 만든 뒤:

```bash
git rebase --continue         # 뒤따르던 커밋을 다시 얹는다
```

대상이 HEAD 면 rebase 없이 `git reset --soft HEAD~1` 만으로 같다. 반대로 `git reset --soft HEAD~N` 으로 여러 개를 한꺼번에 푸는 것은 뒤따르던 커밋까지 녹여 워킹트리에 섞는다 — 대상 하나만 푸는 것이 `edit` 이다.

**새로 만든 커밋의 작성일은 오늘이 된다.** 방금 만들어진 커밋을 고치는 것이면 잃을 것이 없지만, 오래된 커밋을 다시 나누면 언제 작업했는지가 사라진다. 그것이 아까우면 분할을 그대로 두고 메시지만 고친다.

## 되돌리기

`git reflog` 에 rebase 이전 HEAD 가 남는다. `git reset --hard <그 해시>` 로 돌아간다. 푸시까지 마쳤다면 아직 당기지 않은 클론이 옛 이력을 온전히 들고 있다.

## 그대로 두는 것

`revert`·`cherry-pick`·머지처럼 git 이 메시지를 만든 커밋은 손대지 않는다.
