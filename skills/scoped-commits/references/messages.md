# 메시지 규칙

`SKILL.md`의 3단계에서 분할이 확정된 뒤에 읽는다.

## scope

제목은 `<scope>: <설명>` 이다. scope 는 이 커밋이 바꾼 함수·상수·규칙의 **공통 목적**을 가리키는 이름이다.

- **영역을 앞에 세운다.** 로그를 훑는 사람이 알고 싶은 것은 변경의 종류가 아니라 어느 영역을 건드렸는가다. `feat`·`fix`·`chore` 같은 분류는 대체로 한 값에 쏠려 제목의 앞자리만 먹는다. 다만 그 프로젝트에 `test/`·`build/` 같은 영역이 실제로 있다면 그건 분류가 아니라 영역 이름이므로 그대로 쓴다.
- **그 영역을 부르는 이름 그대로 쓴다.** 프로젝트가 `net/http/cookiejar` 라고 부르면 그렇게 쓴다 — 슬래시·점·대문자가 들어가도 그것이 통용되는 이름이면 그것이 맞다(`nixosTests.fail2ban`, `MAINTAINERS`). 통용되는 이름이 없어 새로 지을 때만 소문자 kebab-case 로 짓는다.
- **파일이 무엇을 하는지를 가리킨다.** `src`·`lib`·`test`·`deps`·`skills` 처럼 담는 통의 이름은 마지막 수단이다 — 그 통 안의 모든 커밋에 같은 이름이 붙어 아무것도 좁혀 주지 못한다. 경로인지 아닌지는 기준이 아니다. `net/http/cookiejar` 는 경로이면서도 하는 일을 가리키므로 좋은 scope 다.
- 이 커밋 하나만 가리키는 이름은 너무 좁다. 저장소의 절반을 덮는 이름은 너무 넓다.
- 두 층 사이에서 망설이면 **더 구체적인 쪽**을 골라라.
- **테스트·ADR·README는 부수물이다.** 영역으로 세지 않는다. 코드와 그 테스트와 그 문서를 함께 고친 커밋의 scope는 코드 쪽 영역이다.
- 문서 저장소에서는 문서가 부수물이 아니라 실체다. 이때는 그 문서가 다루는 **개념**이 scope다.
- 한 커밋의 scope는 하나다. 실체 영역이 여럿이면 그중 하나를 대표로 쓰고, 나머지는 본문에서 말한다.

### 과거 scope 조회

```bash
git log -n 30 --format=%s -- <이 커밋이 바꾸는 파일들> \
  | grep -oP '^[A-Za-z0-9][A-Za-z0-9._/-]*(?=: )' \
  | grep -vE '^(feat|fix|chore|refactor|style|perf|revert)$'
```

여기서 나온 이름은 **후보이지 기본값이 아니다.**

- 재사용 자체는 목표가 아니다. "가능하면 재사용하라"는 압력을 주면 틀린 이름을 물려받고, 그 이름이 다음 커밋의 후보가 되어 번진다.
- **같은 파일을 건드렸다는 사실은 같은 영역이라는 근거가 아니다.** 한 파일 안에 여러 영역이 산다.
- 목록의 이름을 쓰려면 근거를 diff에서 찾아라 — 이 커밋이 바꾼 함수·상수가, 그 이름이 가리키는 것과 같은 목적을 위해 존재하는가.
- 근거를 못 찾으면 새 이름을 지어라.
- 근거를 찾았더라도, 그 이름이 가리키던 것이 이 커밋에서 **실제로 리네임됐다면** 새 이름을 지어라.

## 제목

- scope와 `: ` 를 포함해 **72칼럼 이내.** 한글은 한 자가 2칼럼이라 순한글이면 36자다. 그 너머는 GitHub이 말줄임으로 자르고 `git log --oneline` 한 줄이 넘친다.
- **"~한다"** 로 끝낸다. 의문형이나 명사형이 떠오르면 같은 뜻을 평서형으로 고쳐 쓴다 — "왜 느린가" 가 아니라 "느린 원인을 찾는다", "훅 정리" 가 아니라 "훅을 정리한다".
- 마침표를 붙이지 않는다.
- 제목이 한 줄로 요약되지 않으면 `SKILL.md` 2단계로 돌아간다.

## 본문

**모든 커밋에 본문을 쓴다.** `검증:` 같은 머리표 없이 산문으로 쓴다.

세 가지를 담는다.

1. **왜 이 변경을 했는가.** 무엇을 했는지는 diff가 말한다. 본문은 왜인지를 말한다.
2. **고려했다가 하지 않은 것과 그 이유.** 무엇을 일부러 뺐는지 적지 않으면 다음 사람이 그것을 빠뜨린 것으로 읽고 채워 넣는다.
3. **확인하지 못한 것은 확인하지 못했다고 밝힌다.** 어디까지가 실측이고 어디부터가 추정인지 적는다.

수치가 있으면 수치를 적는다. 무엇이 움직였고 무엇이 그대로인지가 리뷰어에게 가장 빠른 정보다.

## 커밋 실행

해당 변경만 `git add`로 스테이징하고 커밋한다. 본문이 길면 `git commit -F -`에 heredoc으로 넘기는 것이 따옴표 처리가 없어 안전하다.

## 로그 점검

규약을 어긴 커밋을 커밋 시점에 잡아 주는 층은 없다. 대신 언제든 로그를 통째로 훑어 표류를 찾는다.

```bash
T='feat|fix|docs|chore|refactor|style|test|build|ci|perf|revert'
git log --no-merges --format='%s' | grep -vE '^[A-Za-z0-9][A-Za-z0-9._/-]*: [^ ].*[^.。．｡…]$'
git log --no-merges --format='%s' | grep -E "^($T)(\([^)]*\))?: "
```

첫 줄은 `<scope>: <설명>` 형태를 벗어난 제목과 마침표로 끝나는 제목을, 둘째 줄은 type 접두어를 찾는다. 둘째 줄은 넓게 잡으므로 그 프로젝트의 실제 영역 이름(`test/`·`build/` 를 가진 저장소의 `test:`·`build:`)은 눈으로 걸러 낸다 — 게이트가 아니라 보고서다.

**잡지 못하는 것**: 제목 폭, `~다` 종결, 본문 유무와 내용, 분할이 옳은지. 그것들은 커밋을 만들 때 이 문서가 맡는다.
