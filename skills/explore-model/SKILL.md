# Explore Model

설계한 상태 모델을 순수 리듀서로 세우고, 도달 가능한 상태를 **전부** 훑어 설계 결함을 구현 전에 찾는다.

사람이 손으로 모델을 몰아보는 것(`/prototype` 의 LOGIC 가지)과 목적은 같고 탐색자가 다르다. 손으로 밟을 수 있는 명령열은 수십 개고 전부 **자기가 상상한** 시나리오인데, 설계가 틀린 지점은 대개 상상하지 못한 조합에 있다. 상상했다면 설계할 때 이미 반영했을 테니까.

**탐색은 기계가, 판정은 사람이.** 이 스킬은 판정을 대신하지 않는다.

## 언제 쓰는가

네 가지가 **전부** 참일 때만 값이 난다:

1. 모델을 `(state, action) => state` 순수 함수로 세울 수 있다
2. action 집합이 유한하고 열거 가능하다
3. 상태를 정규화해 동등 비교할 수 있다 (직렬화 가능)
4. **코드를 다시 읽지 않고 문장으로 진술할 수 있는 규칙이 최소 하나 있다** — "결제된 주문은 취소 후에도 환불 대상이다", "잔액은 음수가 될 수 없다"

4번이 없으면 멈춰라. 주장할 것이 없는 탐색은 상태 목록만 뱉는다.

잘 걸리는 곳: 상태기계, 승인/결재 워크플로, 권한 판정, 잔액·정산, 예약·재고, 재시도·타임아웃이 얽힌 흐름.

쓰지 않는 경우:

- **"이게 어떻게 보여야 하나"** → `/prototype` 의 UI 가지
- **"이 설계가 그럴듯하게 느껴지나"** — 판정이 취향에 가까우면 → `/prototype` 의 LOGIC 가지. 사람이 손으로 모는 편이 빠르다
- **결정이 아직 안 섰다** → `/grill-me` 로 먼저 결정을 닫는다. 모델이 없으면 탐색할 것도 없다
- **이미 구현된 코드의 버그를 찾는 중** → `/diagnosing-bugs`. 이 스킬은 구현 전용이다
- **회귀 테스트가 목적** → `/tdd`. 아래 "테스트를 만들지 않는다" 참조

## 절차

### 1. 질문과 규칙을 적고 승인받는다

탐색기를 짜기 전에 두 가지를 적어 사용자에게 확인한다.

- **질문** — 이 탐색이 답할 것 한 문장. "결제·취소·환불이 섞였을 때 도달 불가능해야 할 상태에 도달하는가?"
- **규칙(불변식)** — 모든 도달 가능 상태에서 참이어야 하는 명제 목록.

**승인되지 않은 규칙으로는 판정하지 않는다.** 규칙을 스스로 발명하지 마라 — 그러면 이 탐색이 검증하는 것은 설계가 아니라 규칙을 지어낸 쪽의 이해가 된다. 규칙의 출처는 넷뿐이다: 사용자, `CONTEXT.md`/ADR, 기존 구현, 변형 관계(왕복·멱등성).

`CONTEXT.md` 가 있으면 먼저 읽고 그 용어로 규칙을 쓴다.

### 2. 모델을 순수 리듀서로 세운다

`/prototype` 의 LOGIC 가지와 같은 규율을 쓴다 — I/O 없음, 출력 없음, 전역 상태 없음. 리듀서는 이 탐색이 끝난 뒤 실코드로 올라갈 유일한 산출물이다.

프로젝트가 쓰는 언어로 쓰고, 프로젝트의 태스크 러너에 실행 명령을 하나 등록한다.

**모델이지 구현이 아니다.** 실제 필드를 다 옮기지 마라. 질문에 답하는 데 필요한 상태만 담는다.

### 3. 범위를 좁힌다

상태공간은 쉽게 폭발한다. 폭발을 막는 것은 반칙이 아니라 기법이다 — **대부분의 반례는 작은 범위에서 이미 나타난다**(Alloy의 small scope hypothesis).

- 금액은 `{0, 1, MAX}` 세 값으로
- 사용자·주문은 2개로 (1개는 상호작용을 못 만들고, 3개는 대개 2개가 못 찾은 것을 못 찾는다)
- 시간은 틱 3~5개로

좁힌 범위를 탐색 보고에 **명시한다.** 범위를 밝히지 않은 "안 깨졌다"는 아무 뜻이 없다.

### 4. 전수 탐색한다

초기 상태에서 BFS로 도달 가능한 상태를 전부 방문한다. 라이브러리는 대개 필요 없다.

```
frontier = [초기상태]
seen     = { key(초기상태): [] }          # key -> 거기까지의 명령열
violations, dead = [], []

while frontier and len(seen) < LIMIT:
    s = frontier.pop(0)
    for a in actions(s):                  # 이 상태에서 합법인 액션만
        n = reduce(s, a)
        path = seen[key(s)] + [a]
        for rule in RULES:                # 1단계에서 승인받은 규칙
            if not rule.holds(n):
                violations.append((rule.name, path, n))
        if key(n) not in seen:
            seen[key(n)] = path
            frontier.append(n)

dead = [s for s in DECLARED_STATES if key(s) not in seen]
```

`key()` 는 정규화된 직렬화다 — 순서가 안정적이어야 같은 상태를 두 번 안 센다.

`LIMIT` 에 걸리면 **멈추고 그 사실을 보고한다.** 조용히 자르면 "안 깨졌다"가 거짓말이 된다. 걸렸다면 3단계로 돌아가 범위를 더 좁힌다.

### 5. 네 가지로 보고한다

| 산출물 | 뜻하는 것 |
|---|---|
| **도달 가능한 상태** | 몇 개인지, 그리고 의외인 것 몇 개를 명령열과 함께 |
| **도달 불가능한 상태** | 설계에 선언했는데 아무 명령열로도 못 감 → 모델이 **과잉** |
| **규칙을 위반하는 상태** | 설계 결함. 이 탐색의 본체 |
| **표현 불가능한 시나리오** | 도메인에선 일어나는데 이 모델로 못 그림 → 모델이 **부족** |

두 번째와 네 번째는 테스트로는 절대 안 나온다. 테스트는 있는 것만 확인하지, 없어야 할 것과 없는 것은 못 짚는다.

**반례는 명령열 원문 그대로 낸다.** 요약하지 말고, "이건 버그다"라고 단정하지도 마라 — 판정은 사용자가 한다. 규칙 위반이 아니어도 **의외인 도달 가능 상태**는 보고한다. 설계 결함이 규칙의 빈틈으로 새는 자리가 거기다.

### 6. 판정을 남긴다

사용자가 판정하면 그 결과를 문서로 고정한다. 코드가 아니라 문서다.

- **ADR** (`/domain-modeling` 의 ADR-FORMAT) — 모델을 고쳤거나, 대안을 두고 이걸 골랐다면. "도달 가능 상태 N개, 그중 X는 도달 불가라 모델에서 뺐다"
- **`CONTEXT.md`** — 탐색 중 드러난 용어의 모호함. 규칙을 문장으로 쓰다 보면 반드시 나온다
- **리듀서** — 검증된 모델은 실코드로 올린다. 탐색기 껍데기는 버린다

## 규칙

- **기대값을 발명하지 않는다.** 규칙은 1단계에서 승인받은 것만. 탐색 도중 "이것도 규칙이겠네" 싶으면 실행하지 말고 사용자에게 물어 목록에 추가한 뒤 다시 돌린다.
- **탐색기는 버림 코드다.** 남는 것은 리듀서와 판정 문서뿐. 탐색기에 테스트를 붙이거나 일반화하지 않는다.
- **테스트를 만들지 않는다.** 이 스킬의 산출물은 설계 판정이지 회귀 테스트가 아니다. 발견한 반례를 테스트로 얼리고 싶으면 `/tdd` 로 넘기되, 기대값은 사용자가 판정한 그것을 쓴다 — 탐색기가 계산한 값을 그대로 쓰면 tautological 테스트가 된다.
- **모델이 폭발하면 모델을 줄인다.** 탐색기를 최적화하거나 LIMIT를 올리지 마라. 폭발 자체가 모델이 너무 많은 걸 담고 있다는 신호인 경우가 많다.
- **검증된 것은 모델이지 코드가 아니다.** 보고에 이 한계를 적는다. 설계가 맞아도 구현이 다르면 소용없다.

## 예시

```
> /explore-model 주문 상태기계 — 결제·취소·환불이 겹칠 때

질문: 환불된 주문이 다시 결제 가능 상태로 돌아갈 수 있는가?

규칙 (승인 필요):
  R1. 환불된 주문은 어떤 명령열로도 결제됨 상태로 돌아가지 않는다
  R2. 총 환불액은 총 결제액을 넘지 않는다
  R3. 취소된 주문에는 배송이 붙지 않는다

범위: 주문 1개, 결제 시도 최대 2회, 부분환불 허용

→ 승인 후 탐색

도달 가능 상태 34개 (LIMIT 미도달, 전수 완료)
R1 위반 1건:
  [결제] → [부분환불] → [취소] → [재결제]  ⇒ 환불됨 + 결제됨 동시 성립
R3 위반 0건
도달 불가능: PARTIALLY_SHIPPED (선언했으나 도달 경로 없음)
표현 불가: "결제 실패 후 다른 수단으로 재시도" — 모델에 결제수단 개념이 없음

판정 요청: R1 위반은 실제 결함인가, 아니면 R1이 너무 강한가?
```
