# benchmark

성능 비교 판단("A와 B 중 뭐가 빨라?")을 실측으로 판정할 때의 측정 방법론. 규칙 원문은 [`SKILL.md`](SKILL.md)에 있고, 여기는 절차가 왜 이 모양인지의 근거를 적는다.

## 왜 스킬인가 — 전역 규칙만으로는 경계 실측이 빠진다

전역 CLAUDE.md에 "추천 전에 돌려본다" 규칙을 넣고, `list(map(str, xs))` vs `[str(x) for x in xs]` 함정 문제(람다가 끼면 승자가 뒤집힌다)로 실측했다 (2026-09-01, sonnet, `claude -p` 반복 실행):

| 구성 | 경계(람다 뒤집힘) 실측 |
|---|---|
| 전역 규칙만 — 방법 한 줄 포함 3변형 | 0/3 |
| 스킬 설치했으나 미발동 | 0/2 |
| 스킬 발동 | 6/6 |

방법의 "언제"(전역 규칙)와 "어떻게"(도메인 방법론)를 나눈 이유다. 발동률도 측정했다: 설명문 초안 1/2 → "언제 쓰는지" 중심으로 강화 2/3 → CLAUDE.md에 "측정 방법론 스킬을 먼저 연다" 배선 한 줄 추가 3/3.

## 절차별 근거

- **경계부터 설계한다**: 스킬 없는 세 조건 모두 질문에 적힌 형태만 재고 일반화했다. 정답은 조건부다 — 내장 `str`이면 map이 ~7% 우세, 람다·사용자 함수가 필요하면 컴프리헨션이 우세(8~34%, 측정 세션별).
- **best 기준·순서 스왑**: 같은 문제를 평균 기준으로 재면 "map 6~7% 우세", 순서 스왑+best 기준으로 재면 "잡음 수준 동률"로 결론이 갈렸다. 측정 방법이 결론을 바꾼다.
- **조건부 보고**: 단일 승자를 뽑으면 경계 반대편 조건의 사용자를 틀리게 만든다.

## 한계

셀당 2~3회, sonnet, 파이썬 마이크로벤치마크 한 종류로 얻은 근거다. 발동 시 6/6이 100%를 보장하지 않는다. 메모리·부하·동시성 측정은 이 스킬의 범위 밖이다 — 그 영역에서 방법이 엉성한 사례가 관찰되면 별도 스킬로 뽑는다.
