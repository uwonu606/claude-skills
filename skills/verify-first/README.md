# verify-first

추천을 말하려는 순간 검증 가능 여부를 가르고, 가능하면 전문 측정 에이전트로 넘기는 라우터. 규칙 원문은 [`SKILL.md`](SKILL.md), 측정 기법은 [`agents/`](agents/) 의 에이전트 정의에 있고, 여기는 절차가 왜 이 모양인지의 근거를 적는다. 함정 문제와 정답은 [`references/traps.md`](references/traps.md). 흡수한 두 스킬의 근거 기록은 [`references/benchmark/`](references/benchmark/), [`references/change-probe/`](references/change-probe/).

## 파이프라인

```
전역 CLAUDE.md "추천하기 전에 돌려본다"            ← 언제
  └ verify-first  (추천 문장이 나오려는 순간)      ← 어떻게의 총론
      1 갈리는 관찰값 한 문장
          못 쓰면: 사람 안 ③ / 출처 ② / 오라클이 미래 → 근사 또는 불가 이유
      2 비용 문: 코드 말고 무엇을 되돌리나 + 틀렸을 때 언제 아나
          코드뿐이면 안 재고 답 | 재면 예보 묻기(대화 중) 또는 흔한 요구 가정
      3 관찰값 모양 → 전문 에이전트                   ← 어떻게의 각론
          실행 시간·처리량·지연 ..... agents/perf-prober
          요구 변경 뒤 복원·계약 .... agents/change-prober
          도달 불가 상태 ............ explore-model 스킬
      4 맞는 전문가 없음 → general-purpose + 공통 뼈대
      5 조건부 보고 + 근거 등급 + 가정
  옆 장치
      scripts/audit-misses.py  세션 감사 → 사람 입장 심사 → 소급 측정 → 함정 추가
      references/traps.md      정답 확정 함정으로 유무 A/B, 기준은 돌리기 전 등록
      install.sh               SKILL.md → ~/.claude/skills, agents/*.md → ~/.claude/agents
```

## 왜 이 모양인가 — 진입점 하나, 기법은 에이전트

benchmark·change-probe 는 각각 한 영역(성능, 되돌리기 비싼 결정)의 측정 방법론으로 먼저 있었다. 그 방식은 영역마다 스킬을 하나씩 뽑아야 하고 관찰된 실패가 있어야 뽑는다. 질문의 종류는 그보다 많아, 영역을 특정하지 않고 "추천이 나오려는 순간"에 들어가는 라우터가 필요했다.

라우터를 도메인 스킬 옆에 두는 첫 모양은 1라운드 A/B 에서 깨졌다 — 설명문끼리 발동 경쟁을 하면 라우터는 도메인 스킬이 안 잡는 자리에서만 열린다(4/6 vs 0/12). 반대로 도메인 스킬을 빼고 라우터만 두면 열리기는 하는데(6/6) 도메인이 알던 경계를 못 찾는다(람다 0/3, 이력 요구 0/3). 그래서 두 스킬을 스킬 목록에서 빼고 측정 기법을 전문 에이전트 정의로 옮겼다. 라우터가 관찰값 모양으로 에이전트를 고르고, 기법은 에이전트 시스템 프롬프트 안에 산다.

이 갈래를 고른 이유가 셋이다. 위임 준수 — 라우터만 둔 P1 에서 2/3 이 4단계를 무시하고 부모가 직접 쟀는데, "참조를 읽고 프롬프트를 써라"보다 "이 관찰값이면 이 에이전트"가 행동이 구체적이다(감, 새 A/B 로 잰다). 문 지기와 기법의 분리 — change-probe 1단계는 비용 문과 배정 조건이 한 문단에 있었고, 합치면 비용 문은 라우터 2단계, 배정 조건은 3단계로 갈라진다. 부모 컨텍스트 — 기법이 에이전트 안에 있으면 부모가 읽지 않는다.

과적합 우려는 절반만 맞았다. 라우터만 둔 P2 가 틀린 지점("기록 안 한 과거는 못 살린다, '나중에 얹으면 된다'는 실측 대상")은 주문 도메인의 사실이 아니라 되돌리기 비용의 일반 원리다. 반면 benchmark 의 결정적 경계(람다 감싸기)는 파이썬 함수 호출 비용이라 언어 특정 사실이고, 그대로 적으면 과적합이다. 에이전트 정의는 이를 "실행 경로를 바꾸는 사용 방식" 원칙 + 파이썬 사례로 적었다. 과적합 여부는 파일 위치가 아니라 **작성에 쓰지 않은 함정**으로 잰다 — 아래 사전 등록의 H1·H2.

## 두 실측이 이 설계에 대해 말하는 것

이 저장소의 앞선 두 실측(등급 ①)이 라우터가 어디서 깨지는지를 미리 보여 준다.

| 실측 | 조건 | 결과 | 라우터에 주는 뜻 |
|---|---|---|---|
| change-probe 기준선 (2026-09-02, sonnet 3판) | 전역 규칙 + benchmark 설치, status 컬럼 vs 이벤트 로그 | 3/3 이 "벤치마크 대상이 아니다"로 분류하고 실측 없이 닫음. 실측하면 그 답은 틀림 | **분류는 아래로 틀린다.** 검증 가능한 것을 불가능으로 분류하는 것이 모델의 기본값이다. 분류를 판단에 맡기면 안 된다 |
| benchmark 기준선 (2026-09-01, sonnet 3판) | 전역 규칙만, map vs 컴프리헨션 | 재긴 쟀으나 경계 변형 0/3, 평균 기준이라 결론이 갈림 | **분류를 통과해도 방법 없이 재면 틀린다.** "적합한 에이전트"의 적합함은 프롬프트에 든 방법론이 정한다 |
| change-probe 함정 (가) | if 분기 vs dict 등록, 8칸 실제 구현 | 전 칸 동률. 입장 거부에도 판당 40~50초 | **검증 가능인데 재면 동률인 영역이 있다.** 리팩토링으로 돌아오는 선택은 재도 돈만 쓴다 |

## 절차별 근거

- **1단계 "갈리는 관찰값 한 문장"**: 분류를 "검증 가능한가"라는 판단 대신 "관찰값을 적을 수 있는가"라는 산출물로 바꿨다. 판단은 아래로 틀리지만 산출물은 있거나 없다. 못 적는 이유를 셋으로 이름 붙인 것은 "검증 불가"가 한 덩어리가 아니기 때문이다 — 출처가 답인 것은 검증 불가가 아니라 실행 불요이고, 오라클이 미래에 있는 것은 근사로 당길 수 있다(change-probe 의 소급 측정이 그 예).
- **2단계 비용 문**: 전역 규칙에 이미 있는 상대 비용 기준("돌리는 비용 < 틀린 추천을 무르는 비용")을 라우터 안에 명시했다. 함정 (가)가 근거다. 사용자 요청 원문은 "검증할 수 있다면 검증"이었고, 비용 문은 그 "할 수 있다"에 값을 매기는 절이다 — 한 절이라 빼기 쉽다.
- **3단계 도메인 스킬 위임**: benchmark 발동 6/6, change-probe 3/3 이 이미 있다. 라우터가 이를 대체할 이유가 없고, 관찰값 문장으로 고르게 한 것은 질문의 겉모양(성능 질문처럼 보임)과 관찰값(실패 조건 아래 성공률)이 갈리는 함정 (다) 때문이다.
- **4단계 공통 뼈대**: 세 도메인 스킬의 교집합이다 — 경계 변형(benchmark 1절, change-probe 3·4절), 잡음 대비(benchmark 2절), 범주적 지표(change-probe 3절), 사전 등록(세 스킬의 README 전부), 조건부 보고(전부). 여기에 "내 결론이 깨질 조건 하나"(전역 CLAUDE.md)와 "모델의 가정 명시"를 더했다. 후자는 함정 (다) 정답 실측에서 유휴 용량 버그가 한쪽 성공률을 2배 부풀린 사건이 근거다.
- **측정 위임**: grilling fork·change-probe 와 같은 근거 — 측정 잔해가 판단 컨텍스트에 쌓이는 걸 막는다.

## 함정 (다) — 도메인 스킬 없는 영역의 정답

재시도 고정 간격 vs 지수 백오프. 단일 승자 답은 어느 쪽이든 틀린다: "지수 + 지터가 표준"(②)은 독립 일시 실패에서 지연을 공짜로 치르고 시도 횟수 고정 + 짧은 장애에서 지터가 성공률을 깎으며, 질문 형태만 잰 "고정이 빠르다"는 동시 폭주에서 77% vs 99% 로 뒤집힌다. 갈리는 축은 정책 이름이 아니라 실패 모델(독립·장애·폭주·백로그)과 지터 유무다. 표와 가정은 [`references/traps.md`](references/traps.md).

## 유무 A/B — 사전 등록

change-probe 와 같은 프로토콜: sonnet, `claude -p`, 스킬은 설치만 하고 호출은 명시하지 않는다. 판정 기준은 돌리기 전에 여기 박는다. 합격은 각 셀 3판 중 2판 이상, 본문 수정은 최대 2회, 판당 시간·비용을 기록한다.

| 셀 | 질문 | 합격 기준 |
|---|---|---|
| P1 양성·도메인 있음 | map vs 컴프리헨션 (benchmark 함정) | 이 스킬 로드 → benchmark 로드. 경계(람다) 실측. 조건부 |
| P2 양성·도메인 있음 | status 컬럼 vs 이벤트 로그 (change-probe 함정) | 이 스킬 로드 → change-probe 로드. 요구 예보를 묻거나 조건부 |
| P3 양성·도메인 없음 | 재시도 함정 (다) | 시뮬레이션 실측(도구 호출). 실패 모델 경계 변형 2개 이상. 조건부. 정답 정합: "독립 실패에서 고정이 지연 우위"와 "폭주에서 지터 우위" 중 하나 이상 재현 |
| N1 음성·출처 | REST vs GraphQL | 시뮬 0회. "출처가 답" 지목, 등급 ② |
| N2 음성·취향 | fetchUser vs getUser | 시뮬 0회. "판정 기준이 사람 안에" 지목, 등급 ③ |
| N3 음성·되돌리기 쌈 | if 분기 vs dict 등록 | 시뮬 0회 또는 짧게. 비용 문으로 거부 |

발동은 기록의 스킬 로드 흔적으로 잰다. P3 가 이 스킬의 진짜 시험이다 — 공통 뼈대만으로 도메인 스킬 없는 영역이 제대로 재지는지는 아직 반반이다. P3 에서 benchmark 로 잘못 넘긴 판이 나오면 3단계의 "관찰값으로 고른다" 문장이 작동하지 않은 것이므로 따로 센다.

**배선**: 전역 CLAUDE.md 는 현재 도메인 스킬("측정 방법론 스킬이 있으면 먼저 연다")에 배선돼 있고 이 라우터에는 아니다. benchmark 는 배선 한 줄로 발동이 2/3 → 3/3 이 됐다. 먼저 배선 없이 돌리고, 발동이 2/3 미만이면 한 줄 더한 뒤 다시 돌린다 — 두 효과를 분리해 기록한다.

**예상 비용**: 여섯 셀 × 3판 = 18판. change-probe 실측 기준 양성 판당 $0.34~0.84, 음성 판당 $0.06~0.11 이라 $5~10 사이.

비용·시간: 22판 $5.82. 기준선 판당 $0.07~0.14, 59~69초. 라우터가 시뮬레이션까지 간 P3 3번 판 $0.81, 584초. N1 1번 판 $2.99, 899초.

**읽는 법.**

- **라우터는 도메인 스킬 설명문이 안 잡는 자리에서만 열린다** — P3·N2 에서 2/3, 나머지 넷에서 0/12. 설계 비교 질문은 change-probe 가, 속도 질문은 benchmark 가 발동 경쟁에서 이긴다. 그 자체는 README "한계" 절에 적은 대로 허용한 경로이고 P1·P2·N3 의 결과도 맞다. 다만 등록한 P1·P2 기준("라우터 → 도메인")은 글자대로 0/6 이다.
- **열리면 두 갈래다.** P3 3번 판은 SKILL.md 그대로다 — 관찰값 한 문장을 쓰고, 세 도메인 스킬이 안 맞는 이유를 대고, 경계 변형 둘·깨질 조건·seed 5·범주적 지표·사전 등록 기준·가정 명시·조건부 보고를 전부 실은 프롬프트로 위임해, "독립 실패면 고정이 지연에서 낫고, 과부하면 지수가 방향은 유리하나 등록 기준 10%p 를 못 넘었다"는 조건부 결론을 냈다. 함정 정답과 정합한다. 반면 2번 판은 열고 나서 관찰값 문장을 쓰지 않고 곧장 WebSearch 로 가 "AWS·Stripe 표준 → ②" 로 닫았다 — 1단계의 "출처가 답" 이 탈출구로 쓰였다.
- **N1 이 이 스킬이 막아야 할 과측정을 보여 준다.** change-probe 는 REST vs GraphQL 을 "외부에 노출된 계약"으로 3/3 입장했고, 한 판은 서브에이전트 셋으로 Express·GraphQL 서버를 실제로 지어 요구 네 개를 얹어 쟀다 — $2.99, 15분, 기준 답변의 40배 비용. change-probe 본문은 "언어·프레임워크·엔진 선택은 출처로 판정한다"고 적고 있지만 모델은 그 절을 적용하지 않았다. 라우터가 먼저 열려 "출처가 답"을 지목했다면 막혔을 자리인데, 라우터가 0/3 이라 검증되지 않았다.

### 라우터 단독 실험 (2026-09-06, benchmark·change-probe 심링크 제거, 배선 없음)

"두 도메인 스킬을 지우고 라우터만 둬도 되는가"를 P1·P2 각 3판으로 쟀다. 합계 $3.30.

| 셀 | 라우터 로드 | 잰 것 | 함정의 경계 | 결론 | 판당 비용 |
|---|---|---|---|---|---|
| P1 라우터만 | 3/3 | 크기·큰 정수 변형 timeit. 부모가 직접 잰 판 2/3 | **람다 0/3** | 동률 1, map 추천 1, 크기별 역전 1 | $0.19~0.29 |
| P1 benchmark 있음 (1라운드) | benchmark 3/3 | 크기 + 람다 | 람다 3/3 | 조건부 3/3 | $0.09~0.14 |
| P2 라우터만 | 3/3 | 실측 0/3. 3번 판은 조회 성능을 18분 잰 뒤에야 "기록 형식에 닿는다"에 도달 | **이력 요구 0/3** | "status 컬럼, 확신, 나중에 얹으면 됨" 2/3 | $0.13~2.35 |
| P2 change-probe 있음 (1라운드) | change-probe 3/3 | 예보 묻고 멈춤 | 기록 여부 입장 3/3 | 예보 묻기 3/3 | $0.04~0.08 |

발동은 해결되지만 도메인이 알던 경계를 못 찾는다. 라우터는 "사용 방식 변형"을 크기와 큰 정수로 해석했고, P2 두 판은 change-probe README 가 실측으로 반박해 둔 "나중에 얹으면 된다"로 닫았다. 3번 판은 3단계 표에 적힌 benchmark·change-probe 를 로드하려다 5회 거부당했고(설치돼 있지 않음), 후반의 change-probe 로드는 실험 중 복구한 심링크 때문일 수 있어 그 판의 마지막 답은 단독 조건이 아닐 수 있다. 이 실험이 "지우기가 아니라 흡수"를 결정했다.

### 합친 뒤의 A/B — 사전 등록 (미실행)

같은 프로토콜. 조건은 verify-first + `agents/perf-prober`·`change-prober` 설치, benchmark·change-probe 스킬 없음, 배선 없음. 1라운드에서 본문에 넣은 변경은 셋이고 새 A/B 는 그 묶음을 잰다 — 3단계 에이전트 배정, 1단계 "출처가 답"의 조건(질문의 조건 아래서 확정할 때만), 2단계의 두 번째 질문("틀렸을 때 언제 아나")과 예보 묻기.

| 셀 | 질문 | 합격 기준 (3판 중 2 이상) |
|---|---|---|
| P1 | map vs 컴프리헨션 | 라우터 → perf-prober 위임. 람다 경계 실측. 조건부 |
| P2 | status vs 이벤트 로그 | 라우터 → 예보 묻기 또는 가정 명시 → change-prober 위임. 이주 손실 실측. 조건부 |
| P3 | 재시도 함정 (다) | 라우터 → perf-prober 또는 즉석. 실패 모델 경계 2개 이상. 조건부. 정답 정합 |
| **H1 held-out 성능** | SQL 인덱스 유무를 선택도로 뒤집는 질문 (정답은 먼저 실측으로 확정) | perf-prober 가 선택도 경계를 스스로 넣음. 조건부 |
| **H2 held-out 변경** | traps.md 후보 중 계약 순서 보장 또는 키·파티션 (정답 먼저 확정) | change-prober 가 항목에 맞는 시나리오와 범주적 지표를 스스로 잡음. 조건부 |
| N1 | REST vs GraphQL | 시뮬 0회. "출처가 답" 지목, ② |
| N2 | fetchUser vs getUser | 시뮬 0회. "판정 기준이 사람 안에" 지목 |
| N3 | if 분기 vs dict | 시뮬 0회. 비용 문으로 거부 |

H1·H2 가 과적합 검사다 — 에이전트 정의를 쓸 때 보지 않은 함정에서 2/3 이 나와야 원칙 수준으로 쓰인 것이다. 발동이 2/3 미만이면 전역 CLAUDE.md 배선 한 줄을 더해 다시 돌린다(현재 그 줄은 "측정 방법론 스킬(benchmark 등)"을 가리키고 있어 갱신이 필요하다). 본문 수정 상한 2회. 예상 비용: 8셀 × 3판 = 24판, 양성이 에이전트까지 가면 판당 $0.3~0.9, N 셀 $0.05~0.15 → $6~12. 지금까지 A/B 누적은 $9.1 이다.

| 뺀 것 | 왜 | 넣을 조건 |

| 도메인 스킬을 그냥 삭제 | 라우터 단독 실험에서 람다 0/3, 이력 요구 0/3 — 도메인이 알던 경계를 뼈대만으로는 못 찾는다 | — |
| 방법론을 `references/` 문서로 두고 부모가 읽기 | 라우터만 둔 P1 에서 2/3 이 위임을 건너뛰고 직접 쟀다. 에이전트 배정이 행동이 더 구체적이다 | 새 A/B 에서 에이전트 위임 준수가 2/3 미만이면 |

| 즉석 에이전트의 도메인별 템플릿 | 그게 곧 전문 에이전트다. 같은 골격이 반복되면 그때 `agents/` 에 뽑는다 | 4단계 판에서 같은 시뮬 골격이 3회 이상 반복되면 |

## 한계

- 합친 모양의 A/B 는 미실행이다. 1라운드(도메인 스킬 옆에 둔 모양)에서 P3·N1 불합격, 라우터 단독 실험에서 람다·이력 요구 0/6 — 지금 모양은 그 둘의 실패에서 귀납한 것이고 효과는 아직 주장이다. 라우터가 열려 설계대로 간 사례는 P3 3번 판 하나다.
- 에이전트 정의는 두 SKILL.md 의 기법을 원칙 수준으로 다시 쓴 것이라, 원래 스킬이 자기 함정에서 냈던 6/6·3/3 이 에이전트로도 유지되는지는 새 A/B 의 P1·P2 가 답한다.
- `claude -p` 가 `~/.claude/agents/` 의 사용자 에이전트를 잡는지는 실측 전이다. 안 잡히면 A/B 프로토콜을 프로젝트 `.claude/agents/` 로 바꿔야 한다.
- 함정 (다)의 정답은 시뮬레이션 모델의 가정(FIFO 큐, 서비스 시간 0, 도착 0.1s 집중, 전체 지터)에 묶여 있다. 실측 벤치마크가 아니라 합성 함정이라 change-probe 함정 (나)보다 낮은 ①이다.
- 검증 불가 사유 셋은 이 저장소에서 관찰된 사례에서 귀납한 것이다. 분류가 "위로" 틀리는 경우(오라클이 미래에 있는데 시뮬레이션을 돌려 가정만 쌓는 것)는 대조군이 아직 없다 — traps.md 후보에 있다.
- 세 도메인 스킬과의 경계: 이 스킬은 들어가는 문이고 그쪽은 방이다. 도메인 스킬이 자기 설명문으로 직접 발동하는 경로는 그대로 두며, 라우터는 그 경로가 안 잡은 질문을 잡는다.
