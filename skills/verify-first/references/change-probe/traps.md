# 함정 문제 — 정답이 확정된 것과 후보

스킬의 유무 A/B 는 정답이 실측으로 확정된 함정으로만 돌린다. 함정의 자격: 지금 보기엔 두 설계안이 동률인데, 요구사항 하나가 오면 **범주적으로** 갈리고, 그 요구가 안 오면 반대쪽이 상시 비용을 치른다.

## (나) status 컬럼 vs 이벤트 로그 — 정답 확정 (2026-09-02)

**질문 (기준선·A/B 공통 문구)**: "주문 서비스의 주문 상태(생성→결제→배송→완료, 중간에 취소 가능, 완료 후 환불 가능)를 저장하려고 해. orders 테이블에 status 컬럼 하나로 갈지, 상태 전이 이벤트 로그 테이블로 갈지 추천해줘. 지금 필요한 건 주문의 현재 상태 조회뿐이야."

**정답 실측** (Python 3.14, sqlite in-memory, seed 20260902, 주문 200건·전이 655건, 두 설계에 동일 투입):

| 질의 | A status 컬럼 | B 이벤트 로그 |
|---|---|---|
| Q1 현재 상태 | 100% | 100% |
| Q2 시점 T 상태 | 답 불가 — 근사 20~72% | 100% |
| Q3 delivered 후 refunded 수 | 100% — 상태기계 규칙 덕 (경계 변형 Q3' paid 후 cancelled: 30 vs 정답 17, +76%) | 100% |
| Q4 상태별 평균 체류 시간 | 답 불가 — 오차 356%~ | 100% |
| Q5 주문 전이 이력 | 복원율 12% | 100% |

- **이주 손실**: 요구가 전이 400번째에 도착해 그때부터 A 에 로그를 붙이면, 도착 전 전이가 있던 주문 133건 중 이력 불완전 — 기록만 시작 133/133, 현재 상태 스냅샷 백필 115/133. B 는 0/133.
- **반대 경계** (이력 요구가 영영 없을 때): Q1 코드 A 2줄 / B 5줄. 전체 조회 10^3 건 A 0.22ms / B 1.08ms (4.9배), 10^5 건 24.4ms / 145.2ms (5.9배), 순서 스왑 후 유지. 단건 조회는 1.5배.
- **정답**: 이력·감사·시점 복원 요구가 예정이면 B, 영영 없으면 A. "지금은 A, 나중에 얹으면 된다"는 틀렸다.

**기준선 채점 기준** (돌리기 전 등록): 3판 중 2판 이상이 (1) 요구 예보를 묻거나 조건부로 답하고 (2) 두 안을 실제로 만들어 재면 스킬 불요. 결과: 0/3, 0/3 — 관찰된 실패.

재현 코드: 세션 scratchpad `trap-na/sim.py`, `bench_q1.py` (저장소 밖 — 필요하면 위 사양으로 다시 만든다).

## (가) if 분기 vs 핸들러 등록 테이블 — 함정 자격 없음 (기록용)

알림 발송기(email·slack)에 "kakao 추가 + 채널별 재시도" / "메시지 포맷 전면 변경" 을 넣고, 규모 2종(모듈 1개 / 모듈 3개) × 설계 2종 × 요구 2종 = 8칸을 실제로 구현·변경했다. diff 줄 수 A−B = 1~2, 닿은 기존 함수·깨진 기존 테스트·닿은 파일은 8칸 전부 동률. B 의 딕셔너리 표기를 여러 줄로 바꾸면 29→33→36 으로 A(30) 를 넘는다 — 신호가 표기 잡음보다 작다. 규모를 키워도 격차 0→0.

이유: 코드 구조는 리팩토링으로 되돌아온다. 이 실패가 스킬의 정의("되돌리기 비싼 결정만")를 만들었다.

## 소급 측정 사례 #1 — 미검증 단정 (2026-08-12 세션, 기록 여부)

감사 스크립트가 고른 후보를 소급 측정한 첫 사례. README 의 "실패 관찰 장치" 절이 이 사례로 가동을 확인했다.

**복원** (세션 `-home-ssafy-workspace-alt/7a90e412`, 2026-08-12 02:03): 회의 녹음→STT→이슈(쟁점·결정·할 일) 기록 도구. 후보 (가) = 노션이 정본, 할 일마다 페이지 ID 와 상태를 매핑, "한 일" 발언은 불일치 감지용. 후보 (다) = 할 일은 텍스트만 두고 상태는 이슈 레벨(쟁점→결정됨→실행됨)에만, "한 일" 발언이 전이 근거. 단정 원문: *"(다)를 써본 뒤에 '역시 태스크 단위가 필요하다'가 나오면 그때 (가)를 얹으면 되고, (다)의 이슈 상태는 그대로 삽니다. 순서가 안전합니다."*

**판정** (sqlite 두 저장소, 24회 회의·12회차에 태스크 요구 도착, seed 30 × 조건 5):

| 단정의 전제 | 결과 |
|---|---|
| (다)의 기록만으로 태스크 단위를 소급 복원할 수 있다 | 거짓 — 부분 보고("SDK 붙였어요")를 둘 곳이 없어 버린다. 도착 전 "한 일" 발언 23~37% 귀속 불가, 어느 seed 도 0 아님. 할 일 완료 여부 손실은 노션 성실 1.1% / 반쯤 6.4% / 없음 16.5% |
| (다)의 이슈 상태가 (가) 규칙 아래 그대로 유효하다 | 값은 71~90% 같지만, "실행됨" 이슈의 10~38% 가 (가) 규칙으론 미완료 할 일이 붙은 모순 상태 |
| 노션이 성실히 관리된다 | 조건부 — 사용자가 8분 뒤 택한 조건("노션 안 쓴다")이 손실 최대 경계 |

반대 경계((가) 선행, 요구 영영 안 옴): 회의의 53~77% 에서 "끝났는데 미완료" 할 일이 화면에 남고, 노션 매핑 유지가 6개월 12~115건.

**분류: 미검증 단정.** 단정은 8분 뒤 전제 변경으로 철회돼 실행된 적이 없다. 소급 실측으로는 거짓이고, 싼 보수가 있었다 — "'한 일' 발언을 원문으로 보관" 한 줄이면 손실 0.2~4%. 빠진 결정은 **기록 여부**(입장 항목 1)였다 — 감사 단계에서 항목 2(계약)로 짚은 건 틀렸다.

**가정** (측정 에이전트가 채워 넣고 밝힌 것): (다)는 부분 보고를 저장하지 않음(원문 "할 일에 상태를 주지 않는다"에서 추론) · 회의당 이슈 1~3, 이슈당 할 일 1~4, 완료 주 보고율 0.7, 과대보고 0.2 · 노션 등록률 0.1/0.6/0.95 · 이행 시 매핑은 손으로 100% 성공 · 녹취 재추출은 모델링 안 함. 첫 실행의 집계 버그(0건 seed 누락)와 이행 규칙 불일치를 고친 뒤의 수치이며, 고치기 전 수치는 손실을 위로 치우치게 잡고 있었다 — 방향은 같다.

## 후보 — 입장 항목 2~4 의 함정 (미제작)

- **경계 배치**: 주문·재고를 한 서비스·한 DB 에 둘까 둘로 나눌까 + "재고 차감과 주문 생성의 원자성" 요구. 나뉜 설계는 동시 실패 시뮬레이션에서 정합성 깨짐 건수, 합친 설계는 0. 반대 경계: 독립 배포·확장.
- **계약의 의미 보장**: 이벤트 소비자가 순서에 기대는지 — 파티션을 늘리면 순서가 깨지는 설계 vs 키별 순서를 약속한 설계.
- **기록 형식**: 금액을 float 로 저장 vs decimal — 정산 재계산 요구에서 복원 불가능한 반올림 오차 건수.

관찰된 실패(스킬 없는 세션이 그 항목에서 무조건 단일 승자를 선언한 사례)가 나올 때 만든다.
