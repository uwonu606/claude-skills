# 함정 문제 — 정답이 확정된 것과 음성 대조군

스킬의 유무 A/B 는 정답이 실측으로 확정된 함정으로만 돌린다. 이 스킬의 함정 자격은 change-probe 와 다르다: **도메인 스킬이 없는 영역**에서, 단일 승자 답 — 출처(②)에서 온 것이든 질문 형태만 잰 것이든 — 이 어느 경계에서 틀리고, 시뮬레이션이 그 경계를 드러내야 한다.

도메인 스킬이 있는 셀은 그쪽 함정을 그대로 쓴다: benchmark 의 `list(map(str, xs))` vs 컴프리헨션(benchmark README), change-probe 의 status 컬럼 vs 이벤트 로그(change-probe `references/traps.md`).

## (다) 재시도 고정 간격 vs 지수 백오프 — 정답 확정 (2026-09-06)

**질문 (기준선·A/B 공통 문구)**: "우리 서비스가 외부 결제 API 를 호출하는데 가끔 실패해서 재시도를 넣으려고 해. 1초 간격으로 3번 고정 재시도로 갈지, 지수 백오프(1초, 2초, 4초)로 갈지 추천해줘."

**단일 승자 답이 틀리는 자리**:
- 출처(②)로 답하면 "지수 백오프 + 지터가 표준" — 독립 일시 실패에서 지연 비용을 공짜로 치르고(p99 1.5배), 시도 횟수 고정 + 짧은 장애에서 전체 지터가 성공률을 깎는다(100% → 5~66%).
- 질문 형태("가끔 실패")만 재면 "고정이 빠르고 성공률 같다" — 동시 폭주에서 77% vs 99% 로 뒤집힌다.

**정답 실측** (Python 3.14, 이산 시간 0.05s 시뮬레이션, seed 10개, 값은 seed 간 최솟값~최댓값. 정책 4종: fixed 1s / fixed_jitter U(0.5, 1.5)s / exp 1·2·4·8·16s / exp_jitter 전체 지터 U(0, 상한)):

| 체제 | 조건 | fixed | fixed_jitter | exp | exp_jitter | 갈리는 것 |
|---|---|---|---|---|---|---|
| R1 독립 일시 실패 | p=0.3, K=3 | 성공 97~98%, p99 **2.0s** | 97~98%, 2.4~2.6s | 97~98%, 3.1s | 97~98%, 2.1~2.4s | 성공률 동률. 지연은 고정이 최단 |
| R2 지속 장애, 시도 횟수 K=3 고정 | 장애 1.5s | **100%** (p50 2.1s) | 92~96% | 100% (p50 3.1s) | 47~66% | 창 안이면 고정이 빠르다. 지터는 창을 줄여 손해 |
| | 장애 2.5s | 0% | 14~20% | **100%** | 5~12% | 창 사이면 지수만 산다 |
| | 장애 4.0s | 0% | 0% | 0% | 0% | 창을 넘으면 다 죽는다 |
| R2b 지속 장애, 마감 10s 고정 | 장애 2.5s | 100%, 요청 4.0/클라 | 100%, 3.9~4.0 | 100%, **3.0** | 97~100%, 4.1~4.2, p99 9.1~9.9s | 동률. 고정이 요청 33% 더 보냄 |
| R3b 동시 폭주, 빠른 거절 | N=2000, C=300/s, Q=300, T=1s, K=5 | 77% | 89~90% | 77% | **99~100%** (p99 8.9~9.6s) | 갈리는 건 **지터**. 지터 없는 지수 = 고정 |
| R3 동시 폭주, 백로그 | Q=1000, T=1s (큐 대기 > 타임아웃 → 낭비 작업) | 15% | 15% | 33% | 20~23% | 클라이언트 정책은 아무것도 못 살린다 |
| R3' 같은 조건 + 서버가 오래된 요청 폐기 | | 97% | **100%** (p99 6.7s) | 97% (p99 19s) | 100% (p99 8.5~9.7s) | 서버 쪽 조치가 답. 그 뒤엔 fixed_jitter 꼬리 최단 |
| R3c N=200 (서버 여유) | | 100% | 100% | 100% | 100% | 동률 |

- **정답**: 실패가 독립 일시적이면 고정 간격 — 성공률 같고 지연이 짧다. 동시에 몰리는 폭주가 있으면 지터가 필수이고 지수는 지터의 창을 키우는 역할이다. 지속 장애에서는 시도 창이 장애 길이를 넘느냐가 전부라 정책 이름보다 K·마감이 결정한다. 백로그형 과부하는 클라이언트 정책으로 못 고치고 서버가 오래된 요청을 버려야 한다. "지수 백오프 + 지터"는 폭주 조건의 정답이지 무조건 정답이 아니다.
- **모델의 가정**: 서버는 FIFO 큐(최대 Q)에 처리율 C, 유휴 용량은 저축되지 않음. 클라이언트 타임아웃 T 를 넘긴 요청은 클라이언트가 포기하지만 서버는 모르고 처리한다(R3' 는 서버가 T 넘은 요청을 비용 없이 버림). 도착은 0.1s 안에 몰림. 처리 시간은 큐 대기만 있고 서비스 시간은 0. 요청은 멱등.
- **첫 실행의 버그**: 유휴 용량이 `carry` 에 쌓여 간격이 긴 exp 가 놀았던 시간을 몰아 썼다 — 과부하에서 exp 성공률 96% 가 나왔고, 고치니 77% 였다. R3 과 R3' 이 완전히 같게 나온 것이 단서였다(낭비 작업 기전이 작동하지 않았다는 뜻). 시뮬레이션에서는 승자를 만드는 것이 정책이 아니라 모델 버그일 수 있으므로 "결과가 같아서 이상한 칸"을 먼저 의심한다.
- **순서 스왑**: 결정적 시뮬레이션이라 무의미했다(같은 값). timeit 류 실측에서만 쓰는 장치다.
- **정답 실측 비용**: 시뮬 0.7초. 모델 작성·디버그 포함 1시간.

**기준선 채점 기준** (돌리기 전 등록): 3판 중 2판 이상이 (1) 두 정책을 실제로 만들어 시뮬레이션하고 (2) 실패 모델을 둘 이상 경계 변형으로 넣고 (3) 조건부로 답하면 스킬 불요.

**기준선 결과** (2026-09-06, sonnet 3판, 전역 CLAUDE.md + benchmark·change-probe·explore-model 설치): 시뮬레이션 0/3, 실패 모델 경계 0/3, 세 판 모두 "지수 백오프, 확신, ②(AWS·Stripe)" 단일 승자. 지연 트레이드오프(동기 흐름이면 7초)는 3/3 이 언급했고, 지터와 멱등키도 3/3 이 붙였다 — 출처가 덮는 범위 안에서는 좋은 답이다. 출처가 안 덮는 것(시도 횟수 고정 + 짧은 장애에서 전체 지터의 손해, 백로그형 과부하에서 클라이언트 정책의 무력함)은 0/3. 한 판은 change-probe 를 열어 "코드만 되돌리면 된다"로 입장 거부한 뒤 ②로 답했다. 판당 $0.07~0.14, 59~69초. 관찰된 실패.

**스킬 유 결과** (같은 날, 배선 없음): 라우터 로드 2/3, 시뮬레이션 1/3. 로드한 3번 판은 위임 프롬프트에 경계 변형 둘(독립 저동시성 / 과부하)·깨질 조건·seed·사전 등록 기준을 다 싣고 "독립 실패면 고정이 지연 우위, 과부하면 지수가 방향 우위(+2~9%p, 등록 기준 10%p 미달)"로 조건부 답 — 정답 정합. $0.81, 584초. 지터 미모델링을 한계로 스스로 밝혔다. 로드한 2번 판은 관찰값을 쓰지 않고 WebSearch → ②로 닫았다.

재현 코드: 세션 scratchpad `trap-retry/sim.py` (저장소 밖 — 필요하면 위 사양으로 다시 만든다).

## 음성 대조군 — 검증 불가·불요 (정답: 시뮬레이션을 돌리지 않는다)

| 셀 | 질문 문구 | 정답인 반응 |
|---|---|---|
| N1 출처가 답 | "우리 팀 신규 백엔드 API 를 REST 로 갈지 GraphQL 로 갈지 추천해줘. 프론트는 React, 팀은 4명이야." | 시뮬 0회. "출처가 답"을 지목하고 등급 ②로 조건 붙여 답한다 |
| N2 판정 기준이 사람 안에 | "사용자 조회 함수 이름을 fetchUser 로 할지 getUser 로 할지 추천해줘." | 시뮬 0회. "판정 기준이 사람 안에" 지목, 등급 ③, 팀 관습을 묻거나 한 줄로 답한다 |
| N3 되돌리기 쌈 | "알림 발송기를 채널별 if 분기로 짤지 핸들러 등록 dict 로 짤지 추천해줘. 채널은 나중에 늘 수도 있어." | 시뮬 0회 또는 짧게 끝냄. 2단계 비용 문으로 "코드만 되돌리면 된다"를 밝히고 답한다 |

N3 은 change-probe 의 함정 (가)와 같은 질문이다 — 그쪽에서 8칸 실측 전부 동률이었으므로 재는 것이 낭비라는 정답이 확정돼 있다.

**1라운드 결과** (2026-09-06, 배선 없음): N2 는 라우터 2/3 로드, 시뮬 0/3, 이유 지목 2/3 — 합격. N3 은 change-probe 가 3/3 직접 열려 비용 문으로 거부 — 결과 합격. **N1 은 불합격**: change-probe 가 3/3 직접 열려 "외부 노출 계약"으로 입장했고, 1번 판은 서브에이전트 셋이 Express·GraphQL 서버를 실제로 지어 요구 네 개를 얹어 쟀다 — $2.99, 899초, Bash 79회. 답 자체는 조건부로 나쁘지 않았으나 이 질문에 그 비용은 과측정이다. 이 사례는 change-probe 의 정밀도 공백(본문의 "언어·프레임워크 선택은 출처로" 절이 적용되지 않음)이기도 하다.

## 라우터 단독 실험 (2026-09-06) — 도메인 내용이 필요하다는 근거

benchmark·change-probe 심링크를 빼고 verify-first 만 둔 채 P1·P2 각 3판. 라우터는 6/6 열렸지만 함정의 경계는 0/6 이었다.

- **P1**: 부모가 직접 timeit 을 돌린 판 2/3. 변형은 크기·큰 정수만이고 람다 감싸기는 0/3. 결론은 "동률" 1, "map 7~13% 우세, map 추천" 1, "20개 기준 크기별 역전" 1. benchmark 가 있을 때의 람다 경계 3/3 과 갈린다.
- **P2**: 실측 0/3. 1번 판 "실행해봐도 새 정보가 안 나온다, status 컬럼 확신", 2번 판 "YAGNI, 나중에 필요해지면 얹으면 된다" — 함정 (나)가 실측으로 반박한 문장 그대로. 3번 판은 조회 성능을 재는 에이전트를 18분 돌린 뒤에야 "기록 형식에 닿는다"에 도달했다($2.35). 3단계 표의 benchmark·change-probe 를 로드하려다 5회 거부.

이 실험이 두 스킬을 지우지 않고 `agents/` 로 흡수하는 결정을 만들었다. 에이전트 정의는 이 실험 뒤에 썼으므로 P1·P2 는 더 이상 held-out 이 아니다 — 과적합 검사는 아래 H1·H2 로 한다.

## held-out 함정 — 에이전트 정의를 쓴 뒤에 만든 것 (2026-09-06)

에이전트 정의를 쓸 때 보지 않은 문제라 과적합 검사가 된다. 자격은 (다)와 같다 — 단일 승자 답이 어느 경계에서 틀리고, 실측이 그 경계를 드러내야 한다. 둘 다 정답을 먼저 확정했다.

### H1 인덱스 유무 — 정답 확정

**질문**: "orders 테이블(50만 행)에서 status 컬럼으로 조회해서 금액을 합산하는 쿼리가 자주 나가. status 컬럼에 인덱스를 걸까 말까 추천해줘."

**단일 승자 답이 틀리는 자리**: "WHERE 컬럼엔 인덱스"(②)는 선택도가 높을 때 틀린다. 질문에 적힌 대로 한 선택도만 재면 어느 쪽이든 단일 승자가 나온다.

**정답 실측** (sqlite 3.46, 메모리 DB, 50만 행, `SUM(amount) WHERE status='shipped'` 라 인덱스에 없는 컬럼을 읽어 행 조회가 필요. timeit 5회 최솟값, 순서 스왑):

| 선택도 | 풀스캔 | 인덱스 (플래너가 고름) | 비율 |
|---|---|---|---|
| 1% | 14.6ms | **2.3ms** | 0.16 |
| 10% | 15.8ms | 11.8ms | 0.75 |
| 30% | **19.2ms** | 24.6ms | 1.28 |
| 50% | **20.9ms** | 34.0ms | 1.62 |

- 반대 경계(쓰기): 10만 건 insert+delete 가 인덱스 없이 55ms, 있으면 131ms — 2.4배.
- 플래너는 통계 없이 50% 에서도 인덱스를 고른다. 인덱스가 있다는 것만으로 느려지는 자리다.
- **정답**: 조건에 걸리는 행이 10% 안팎 미만이면 인덱스, 그 위면 풀스캔이 빠르고 인덱스는 쓰기를 2.4배 물린다. 선택도를 모르면 재고 결정한다.
- 가정: 메모리 DB 라 디스크 무작위 읽기 비용이 빠져 있다. 디스크면 인덱스의 불리함이 더 일찍 나타난다.

**등록 기준**: perf-prober 가 선택도 변형을 스스로 넣고(3판 중 2), 조건부로 답한다. 재현 코드: scratchpad `trap-h1/sim.py`.

### H2 파티션 키 — 정답 확정

**질문**: "주문 이벤트(생성·결제·배송·완료)를 Kafka 토픽으로 내보내려고 해. 파티션 키를 주문 ID 로 할지, 키 없이 라운드로빈으로 할지 추천해줘. 지금 필요한 건 처리량뿐이야."

**단일 승자 답이 틀리는 자리**: "처리량뿐이면 라운드로빈"은 순서에 기대는 소비자가 오는 순간 범주적으로 틀리고, 이미 소비된 이력은 못 고친다. "순서 보장하려면 키"는 편중 주문에서 처리량을 물리고 증설 때 순서가 깨진다는 걸 안 말한다.

**정답 실측** (주문 2000, 이벤트 3~5/주문, 파티션 8, 파티션별 소비 지연 U(0,50), seed 10):

| 조건 | A 키=주문 ID | B 라운드로빈 |
|---|---|---|
| 순서 위반 쌍 (순서 요구 도착 후) | **0** | 242~366 |
| 파티션 편중 max/mean, 균등 주문 | 1.01~1.04 | 1.00 |
| 파티션 편중, 5% 주문이 300 이벤트 | 1.16~1.76 | **1.00** |
| 파티션 8→16 증설 중 순서 위반 | 20~71 | 403~553 |
| 이주: B 로 가다 요구가 중간 도착해 A 로 전환 | 도착 전 이미 소비된 위반 83~130 쌍, 주문 1741~1781건 — 복구 불가 | |

- **정답**: 순서에 기대는 소비자가 예정이거나 배제 못 하면 A. 그 요구가 영영 없고 주문별 이벤트 수가 크게 편중되면 B 가 처리량에서 낫다. A 도 파티션 증설 때 순서가 깨지므로 증설 시점의 정지·드레인이 필요하다. "지금은 B, 나중에 키를 넣으면 된다"는 틀렸다 — 도착 전 이력의 뒤집힘은 남는다.
- **첫 실행의 모델 버그**: 증설 행이 A 도 0 으로 나왔다. 두 구간의 소비를 이어 붙여 시간축이 겹치지 않았기 때문이다. 겹치게 고치니 20~71. 조건을 바꿨는데 0 이 그대로인 칸을 의심한 결과다.
- 가정: 파티션별 지연이 독립 균등, 소비자는 파티션 병렬, 이벤트 발행 순서는 주문 내부에서 보존.

**등록 기준**: change-prober 가 "순서에 기대는 소비자" 시나리오와 위반 건수라는 범주적 지표를 스스로 잡고(3판 중 2), 반대 경계를 재고, 조건부로 답한다. 재현 코드: scratchpad `trap-h2/sim.py`.

## 후보 — 미제작

- **분류가 위로 틀리는 함정**: 모델이 "검증 가능"으로 분류해 시뮬레이션을 돌리지만 오라클이 사실 미래·외부에 있어 가정만 쌓이는 질문. 이 스킬의 1단계 세 번째 이유가 제대로 작동하는지 보는 대조군. 예: "온보딩 화면을 3단계로 할지 1단계로 할지" — 전환율은 실사용자에게만 있다.
- **에이전트 오배정 함정**: perf-prober 로 넘겨야 할 것 같지만 관찰값이 실행 시간이 아닌 질문. (다)가 이미 이 성격을 일부 가진다 — A/B 에서 오배정한 판이 나오면 그 판의 결과로 별도 함정 필요 여부를 정한다.
