낯선 레포를 **뛰어난 사람이 읽는 방식**으로 읽는다. 과제에서 출발해 가설을 세우고, 가설에 닿는 코드만 찾아, 돌려서 확인하고, 얻은 것을 **지도**(목표 ↔ 코드 대응)로 남긴다.

지도는 `$REPO_READING_HOME`, 없으면 `~/repo-notes/` 아래 `<레포이름>.md` 하나다. 같은 레포를 전에 읽었으면 그 파일 끝에 새 절로 잇는다.

## 1. 과제를 고정한다

이 읽기가 끝나면 **무엇을 할 수 있게 되는가**를 한 줄로 적는다. 사용자가 말했으면 그대로 쓴다. 안 했으면 사용자가 가장 먼저 만질 법한 기능 하나를 골라 "그 기능이 입력에서 출력까지 어느 파일을 거치는지 짚을 수 있다"로 잡고, 그렇게 잡았다고 밝힌다. "코드베이스를 이해한다"는 과제가 아니다 — 읽을 범위가 안 정해진다.

지도 파일에 절을 열고 머리에 날짜와 과제를 쓴다. 남은 단계는 여기에 이어 쓴다 — 컨텍스트가 요약돼도 확인한 것이 디스크에 남는다.

```markdown
## <날짜> — <과제 한 줄>
### 가설
### 확인
### 왜
### 지도
### 읽은 깊이
```

들어오기 전의 레포 상태를 찍어 둔다. 5단계가 이 값과 대조한다.

```bash
git status --porcelain
```

**완료 기준**: 지도 파일의 과제 한 줄이 "할 수 있다"로 끝난다. `git status --porcelain` 출력을 손에 들고 있다.

## 2. 가설을 세우고 시작점을 잡는다

과제를 개념으로 쪼개고, 개념마다 **어디에 어떻게 구현돼 있을 것이다**를 쓴다. 가설은 틀릴 수 있는 문장이다 — "결제는 `PaymentService` 가 게이트웨이를 불러 처리한다"이지 "결제 코드를 본다"가 아니다.

검색보다 먼저 쓴다. 화면 증상이나 눈에 띈 낱말로 검색부터 하면 엉뚱한 곳에 닿는다 — 실측에서 개발자 9명 중 8명이 증상 "paint" 로 검색해 무관한 메서드로 갔고, 검색의 88% 가 쓸모없었다.

찾은 코드는 세 층으로 가른다.

| 층 | 무엇 |
|---|---|
| 직접 | 과제가 묻는 그 코드 |
| 상호작용 | 직접 코드를 부르거나 직접 코드가 부르는 코드 |
| 길잡이 | 다른 코드를 찾는 데만 쓰는 코드 — main, 라우터, 디스패치 표, 설정 |

**완료 기준**: `가설` 에 틀릴 수 있는 문장이 둘 이상 있고 각각 `미확인` 이 붙었다. 길잡이 층 파일이 나열됐다.

## 3. 돌려서 확인한다

가설마다 직접 코드를 읽고, 그다음 **돌린다**. 확정은 돌려서 본 것에만 붙는다.

- 그 경로를 지나가게 실행하고, 표식(로그 한 줄, 문자열 바꾸기)을 심어 출력에서 본다.
- 일부러 깨뜨려 어디서 어떻게 죽는지 본다 — 스택이 경로를 그대로 보여 준다.

코드를 바꾸는 실험은 1단계 스냅샷에 안 잡힌 깨끗한 파일에만 한다. 5단계에서 되돌린다.

확정된 가설마다 **상호작용 층을 한 홉** 확인한다 — 부르는 쪽, 불리는 쪽, 같은 식별자·설정 키를 쓰는 다른 자리. 필요한 만큼만 읽는 전략이 놓치는 것이 멀리 떨어진 상호작용이고, 국소 단서로 추측한 사람은 절반이 수정에 실패했다.

가설의 표시를 바꾼다.

| 표시 | 뜻 |
|---|---|
| 확정 | 돌려서 봤다. 무엇을 돌려 무엇을 봤는지 적는다 |
| 기각 | 반대 증거가 나왔다. 무엇이 틀렸는지 적는다 — 틀린 가설은 다음 사람의 함정 표지다 |
| 추측 | 읽었지만 못 돌렸다 |

**완료 기준**: `가설` 에 `미확인` 이 없다. `확정` 마다 돌린 것과 본 것이 적혔고, 상호작용 한 홉이 `확인` 에 적혔다.

## 4. 왜를 이력에서 찾는다

읽다가 **왜 이렇게 했지** 싶은 자리마다 이력을 판다.

```bash
git log -S'<식별자>' --oneline -- <경로>
git log --format='%h %an %s' -- <경로> | head
git blame -L <시작>,<끝> <경로>
```

커밋 메시지·PR·이슈·ADR 에 이유가 있으면 **인용**(해시와 함께)이고, 없으면 **추측**이다. 문장을 나눠 적는다. 추측으로 남은 자리에는 blame 이 가리키는 사람을 적는다.

**완료 기준**: `왜` 의 항목마다 인용(해시)이거나 추측 + 물어볼 사람이다.

## 5. 지도를 그리고 닫는다

`지도` 에 과제의 하위 목표마다 코드를 대응시킨다. 한 줄이 한 경로다.

```markdown
- <하위 목표> → `파일:줄` (`함수`) → `파일:줄` — 확정/추측
```

되풀이되는 짜임에는 이름을 붙인다 — 확립된 이름(포트와 어댑터, 커맨드 패턴)이 있으면 그것, 없으면 "이름 없음". 이름이 있어야 찾아볼 수 있다.

`읽은 깊이` 에 전문을 읽은 파일, 일부만 본 파일, 목록으로만 본 것을 나눠 적는다. 지도를 이어 읽을 사람이 어디를 믿고 어디를 다시 볼지 아는 단서다.

실험으로 바꾼 파일을 되돌리고 `git status --porcelain` 을 다시 찍어 1단계 값과 대조한다. 기준은 비어 있는지가 아니라 들어오기 전과 같은지다. 테스트·빌드를 돌렸으면 gitignore 아래 산출물은 git 이 못 보니 무엇을 돌렸는지 적는다.

사용자에게 지도 경로와 `지도` 절을 보여준다.

**완료 기준**: `지도` 의 줄마다 확정/추측이 붙었다. `읽은 깊이` 가 세 갈래다. `git status --porcelain` 이 1단계와 같다. 사용자가 경로를 받았다.
